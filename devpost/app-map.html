MR Solar: app map

A take-home guide to where things live. Snapshot of the code at commit 4801338 on GitHub main; line numbers can drift, so search for the anchors.

What it is

MR Solar shows a stack of merge requests as a solar system. The Sun is main, each planet is an open MR, and stacked branches orbit further out. Cracks mean a merge conflict and a red glow means a failed pipeline. Cascade Sync hands the rebase to Claude Code and heals the train in the UI.

There are two pieces:

  • server.mjs is a dependency-free Node.js server. It holds the demo MR data, serves the page, streams the branch graph over server-sent events, and opens Terminal for Claude.
  • index.html is the whole client: the starfield canvas, the D3 layout, the planets, the hover cards and the action menu.

One action, end to end: Cascade Sync

Reference route

Three stops that follow Cascade Sync through the code. This route wasn't toured live; it's here for when you come back to the project.

  1. The click: index.html, search $('pop-cascade').onclick (about line 2005).
    Posts the selected planet's branch name to the server and updates the status bar. The capsule itself is the #popover markup; showPopover hides the sync buttons on someone else's branch.
    Show the handler 
    $('pop-cascade').onclick = () => {
  if (!selectedNode) return;
  fetch('/api/cascade-sync', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ branch: selectedNode.id }),
  });
  ...
};
  2. The server: server.mjs, search pathname === '/api/cascade-sync' (about line 351) and function syncThenHeal (about line 260).
    Opens Terminal with claude "/cascade-sync <branch>" via openTerminal, collects the clicked branch plus everything stacked on it, marks them syncing, and after SYNC_MS clears conflicts and failed pipelines. Each step calls broadcast, which pushes the whole graph to every open page.
    Show syncThenHeal 
    function syncThenHeal(mrs) {
  mrs.forEach(mr => { mr.syncing = true; });
  cachedGraph = buildGraph(currentScenarioData);
  broadcast(cachedGraph);

  setTimeout(() => {
    mrs.forEach(mr => {
      mr.syncing = false;
      mr.has_conflicts = false;
      mr.pipeline = 'success';
    });
    cachedGraph = buildGraph(currentScenarioData);
    broadcast(cachedGraph);
  }, SYNC_MS);
}
  3. The result on screen: index.html, search es.onmessage (about line 1980), which calls function updateColors (about line 1877).
    Compares each planet's old state with the fresh one. Syncing planets get the node-syncing class (the cyan sync-pulse). Planets that went from broken to healthy fade their cracks and get an expanding heal-wave ring, delayed by stack depth so the wave climbs the train.

A practice to reuse

Check each claimed feature against the running app before ticking it off, and cut or disable what you can't verify.

Evidence from this project: devpost/checklist.md had all four slices ticked, but the final verification (see its Revisions section) found that the scenario switcher and healing animation weren't built, and the Merge button called an /api/merge route the server didn't have. Clicking the real Cascade Sync button later exposed a bug no isolated check had shown: a healed planet turned pink.

The fixes followed the same rule: the switcher was cut, Merge was disabled with a note saying why, and the animation was built and then checked by clicking through the real path. On another project, write the verify step for each feature before building it, and treat "ticked" as "seen working", not "written".
